## 1. 第1段：中身が変わらないファイルは書かない（v20.41）

### 1.1 実測（2026-09-14、kotoba-data 5,228 コミット）

| ファイル | 書いた回数 | うち「日時（updatedAt）だけ」が変わった回数 | 割合 |
|---|---|---|---|
| data.json | 2,136 | **1,640** | 77% |
| training.json | 1,730 | **1,541** | 89% |
| 合わせて | 3,866 | **3,181** | **kotoba-data の全コミットの61%** |

| 置き場所 | 書いた回数 | 何も変わらなかった回数 |
|---|---|---|
| walk10000-data（散歩） | 1,894（8日） | 最新500回のうち **484回（97%）**。中身が同じでも書くたびにコミットが増えることを、同じ中身のコミットが続いていることで確かめた |

- data.json の「日時以外も変わった」496回の中身：言葉 277・端末ごとの使用量 209・日誌 75 など。**これは今までどおり書く**
- 索引（言葉・日誌・瞑想・世界）も数えた。書き直しは全部「月が変わった」印の変化か中身の変化で、**減らせるものは無かった**（ほかの端末に「この月が変わった」と知らせる役なので残す）
- 言葉・日誌・瞑想・世界の月ファイルと、概念・主体などは、**今もすでに中身を比べてから書いている**。変えない

### 1.2 決まり

**「これから書こうとしている中身」と「GitHub に今ある中身」が、日時の欄を除いて1文字も違わなければ、書かない。**

| ファイル | 比べ方 |
|---|---|
| data.json | 書こうとしている文字列（今と同じ作り方）の `updatedAt` を、GitHub にある文字列の `updatedAt` に置き換えて、**GitHub にある文字列と完全に同じ**なら書かない |
| training.json | 同じ |
| 散歩（data.json in walk10000-data） | 書こうとしている文字列が GitHub にある文字列と完全に同じなら書かない（日時の欄は無い） |

- **比べるのは文字列そのもの。** 読み込んで整えた後の形で比べると、整え方の違いで「同じ」と誤って判定する恐れがある。文字列で比べれば、違っていたら必ず書く側に倒れる（多く書くことはあっても、書き漏らすことは無い）
- 古い版の端末が別の並べ方で書いていたら「違う」と判定されて1回書く。それで揃う
- ボタンで押す「上書き」（読み込み・全部消すなど、確かめてから押すもの）は**今のまま必ず書く**
- 同期の表示・最後に同期した日時・未反映の件数は、書かなかったときも「同期済み」にする（取りに行って合わせることはできているため）

### 1.3 失うもの

- GitHub にある data.json・training.json の `updatedAt` が「最後に同期した日時」ではなくなる（「最後に中身が変わった日時」になる）。**アプリの中でこの日時を読んで判断している所は無い**（合わせる時は、ファイル全体の日時ではなく1件ごとの日時で決めている）
- GitHub の履歴で「この日時にこの端末が同期した」が見えなくなる。今も誰も見ていない

### 1.4 見込み

- kotoba-data のコミットは今のペースで**約6割減る**
- 履歴の大きさは**約3割減る見込み**（1コミットの記録とフォルダ一覧で約250バイト、日時だけ違う中身で約50〜100バイト。git の詰め方で変わるので幅がある）
- 散歩の置き場所は、ほぼ伸びなくなる

### 1.5 確かめ

- 偽の GitHub を使った手元の確かめ：①何も変えずに同期→PUT が0回 ②言葉を1件足して同期→data.json の PUT が1回 ③筋トレを1件足す→training.json だけ1回 ④散歩を押す→散歩だけ1回 ⑤GitHub 側だけ別の端末で変わっている→取り込んで、書かない（相手の方が新しいとき）⑥古い並べ方の文字列が GitHub にある→1回書いて、次は書かない
- 実機：両端末で v20.41 にして1日使い、kotoba-data の data.json・training.json のコミットが「中身が変わった時だけ」になっていることを GitHub の履歴で数える（読むだけ）
- 決まった8項目と、打つ・押す確かめ

## 2. 回答書の2（印を別のファイルに置く）：反対。止まります

### 2.1 実測

「印」とは、読む回が札に付ける「読んだ」「書き直した」「切れた推定を読んだ」、★、非表示、ドル換算のこと。

古い月のファイルは、この7日で **6月 13版・7月 18版・8月 28版** 書き直されていた。前後の版を1つずつ比べて、何の欄が変わったかを数えた。

| 変わったもの | 回数（6〜8月の56回の書き直しのうち） |
|---|---|
| **印だけ** | **10回（18%）** |
| 古い日付の札が新しく足された | 23回 |
| 推定（主体の読み）・ずれ・分かれ目・確度など、**読む回が足した中身** | 残りの多く（1回の書き直しで重なる） |

| 古い月の履歴の大きさ（詰めた後） | |
|---|---|
| 2026-06.json（13版） | 10.7KB |
| 2026-07.json（18版） | 20.2KB |
| 2026-08.json（28版） | 28.4KB |
| **（比べて）data.json（2,137版）** | **213.7KB** |

### 2.2 反対の理由

1. **効き目が小さい。** 印だけの書き直しは古い月の書き直しの18%。残りの8割は読む回が推定の文などを札に書き込むためで、印を分けても古い月は書き直され続ける
2. **コミットの数が減らない。** 印を別のファイルに移しても、印を書くたびにそのファイルへのコミットが1回できる。1.1 で分かったとおり、履歴を大きくしているのは中身の大きさより**コミットの数**
3. **消える危険がある。** 今ある札から印を抜いて別のファイルに移す作業が要る。2台の端末の片方が古い版のまま札に印を書くと、2つのファイルで食い違う。合わせる決まりが1つ増える
4. 推定の文まで別のファイルに出す（札を「作った時のまま」に固める）と効き目は出るが、読む回・切れた推定・予告の元の推定・主体の時系列など、**札を読む所を全部作り直す**ことになる。1.1 の「書かない」の何倍も大きく、得られるのは古い月の数KB/週

### 2.3 代わりの案

- **今は分けない。** 第1段で、コミットの一番大きな原因（61%）を先に消す
- 第3段の「置き場所の大きさ」の知らせで、伸び方を**アプリが自分で測り続ける**。もし古い月の書き直しが大きく効いてきたら、そのとき測った数字で、もう一度考える

**決めてほしいこと：** 2 を「今は分けない」でよいか。

## 3. 第2段：読む欄で、端末にあって変わっていない月は取りに行かない（v20.42、案B1）

### 3.1 今

- 読む欄を開くと、索引にある月のうち、**アプリを開いてからまだ読み込んでいない月を全部**読み込む
- 読み込むとき、端末に保存してある月でも**必ず GitHub へ取りに行く**
- 2026-09-14 の索引の月は11個、合わせて約47万バイト。アプリを開くたびに1回。札10枚/日で約200日後に1回約10MB（前の報告）

### 3.2 決まり

月を読み込むとき、次を**全部満たす**なら GitHub へ取りに行かない（端末の分を使う）。

1. 端末にその月が保存してある
2. その月をこの端末で書き換えて、まだ送っていない、ではない
3. 索引にあるその月の「最後に変わった日時」が、この端末が最後に合わせた時の日時と**同じ**

1つでも外れたら今までどおり取りに行って合わせる。

- 索引は同期のたびに GitHub から取っているので、**ほかの端末で変わった月は3で必ず外れて取りに行く**
- 索引をまだ一度も取れていない（アプリを開いてすぐ・通信が無い）ときは、今までどおりにする

### 3.3 失うもの

- 索引が正しく書かれなかったとき（古い版の端末が月だけ書いて索引を書く前に通信が切れた、など）、その月の変更に**次にその月が書き換わるまで**気づかない。今は読む欄を開くたびに取り直すので気づく
  - 備え：同期の中の「今月と先月・書き換えた月」は今までどおり毎回取りに行く（変えない）。気づかないのは古い月だけ
  - 設定に「全部の月を取り直す」ボタンを置く（押したときだけ、今の動きをする）

### 3.4 確かめ

- 偽の GitHub：①読む欄を2回開く→2回目も1回目も、端末にある月は GET 0回 ②別の端末で8月を書き換え（索引の日時も進む）→同期→読む欄→8月だけ GET ③端末で8月を書き換えて送る前→8月は取りに行く ④「全部の月を取り直す」→全部 GET
- 実機：読む欄を開いて、切れた推定・予告の元の札の件数が v20.41 と同じであること

### 4.3 データの置き場所の大きさ（エ）

**何を見るか：** GitHub が返す置き場所の大きさ（KB）。1日1回、その日最初に同期できた時に、kotoba-data と walk10000-data の2つを取る（1日2回増える。今の1時間あたり最大199回の書き込み、上限5,000回/時間に対して小さい）。

- 2026-09-14 に取った値は 2,687KB。手元に写して数えた大きさ（2.45〜2.74MB）と**近いが同じではない**。GitHub がいつ数え直すかは公式の資料に書いてない。**目安として使う**
- 取った値は「日付と大きさ」を端末に残す（90日より古いものは週に1つだけ残す。27年で約1,500件・数十KB）

**伸び方：** 残した値から、**直近90日で1日あたり何KB 伸びたか**を出す。30日分たまるまでは伸び方を出さない。

**出す時（段階）：**

| 段階 | 条件 | 出し方 | あとで |
|---|---|---|---|
| 出さない | 800MB 未満、かつ、この伸び方で1GB に届くのが**6か月より先** | 何も出さない | — |
| **知らせる** | 800MB 以上、**または** 1GB に届くのが6か月以内 | ホームの一番上に1行（ふつうの色） | 30日 |
| **強く知らせる** | 1GB 以上 | 色を強くする | 7日 |
| **消せない** | 3GB 以上 | 毎回出す。同期の表示の横にも出す | 無し |

**なぜ6か月前から・800MB からか（案）：**

- 作業は15〜40分だが、**第4段ができていない時期に出たら、アプリを直す時間が要る**。「あとで（30日）」を何回か押しても間に合う長さとして6か月
- **1GB は「理想は1GB 未満」という目安で、超えても止まる決まりは公式の資料に無い。** 強く推奨の上限は5GB。遅れてもデータは消えないので、12か月以上前から出す必要は無い。早すぎると、何か月も出続けて見なくなる（回答書の条件）
- 伸び方は、本を大量に入れた時などに急に変わる。伸び方だけに頼ると急に「残り2か月」になるので、**大きさそのもの（800MB）でも出す**
- 3GB で消せなくするのは、5GB（強く推奨の上限）に届く前に必ず手を付けるため

**文：**
- 知らせる：「データの置き場所がいっぱいに近づいています（今◯MB・目安1,000MB）。この伸び方だとあと約◯か月。新しい置き場所に引っ越す作業（15〜40分）をしてください」
- 強く／消せない：「データの置き場所が目安を超えました（今◯MB）。引っ越しの作業をしてください。データは消えていません」

### 4.4 押したら出る手順（例：エ）

第4段ができていれば：

1. GitHub で新しい置き場所を作る（押すと GitHub の作る画面が開く）。名前は「kotoba-data-2」など。**「非公開（Private）」を選ぶ**
2. 同期の鍵に、新しい置き場所を足す（押すと GitHub の鍵の画面が開く）。「Contents」を「Read and write」にする
3. このアプリの設定で、置き場所の名前を新しい名前にして「新しい置き場所へ写す」を押す。終わるまでアプリを閉じない
4. もう1台の端末を開く。ホームに「置き場所が変わりました」と出るので、押す
5. （しなくてもよい）GitHub で古い置き場所を「読むだけ」にする

## 5. 第4段：置き場所の名前を設定に・引っ越し（v20.44）

### 5.1 設定

- 設定に「言葉データの置き場所」「散歩データの置き場所」「GitHub の持ち主の名前」を足す。空なら今の名前（kotoba-data・walk10000-data・yutaTasaki）
- 鍵と同じく**端末ごと**に持つ

### 5.2 新しい置き場所へ写す

1. 押すと、古い置き場所の**今のファイルを全部**（最新の版だけ）読み、新しい置き場所に1つずつ書く
2. 書いた後、新しい置き場所から全部読み直して、**古い置き場所と1文字も違わないか**確かめる
3. 全部同じだったときだけ、古い置き場所の data.json に「引っ越した先」の印を書く（5.3）。この端末の設定を新しい名前にする
4. 1つでも違ったら、設定は古いまま。何が違ったかを出す。**古い置き場所は何も変えていない**ので、もう一度押せばよい

- 書き込みの回数：GitHub は「1分に80回・1時間に500回」を目安の上限にしている（公式の資料）。1分に60回までに抑える。27年ぶんの月ファイルでも数百回なので、数分〜十数分
- 途中で閉じた・通信が切れた：古い置き場所は変わっていない。新しい置き場所に半分書かれているだけなので、もう一度押すと続きから（同じ中身のファイルは書かない）

### 5.3 古い置き場所を止める（片方の端末だけ古い所に書く事故を防ぐ）

- 古い置き場所の data.json に「引っ越した先の名前と日時」を書く（data.json は毎回の同期で必ず読むので、読む回数は増えない）
- どの端末も、同期で読んだ data.json にこの印があったら、**その置き場所にはもう何も書かない**。ホームに「データの置き場所が変わりました」と出し、押すと設定が新しい名前になって同期する
- 印は合わせても消えない（新しい方の日時を残す）

### 5.4 失うもの

- 新しい置き場所には**今の版だけ**が入る。過去の版は古い置き場所に残る（GitHub の画面で見られる）。アプリの中の「過去の版」は元々使っていない
- 同期の鍵に新しい置き場所を足すのは人の手（アプリが置き場所を作る案は反対のまま）

### 5.5 確かめ

- 偽の GitHub：①写す→全部同じ→印→切り替わる ②1つだけ中身を変えて確かめさせる→切り替わらない ③途中で止める→もう一度押す→続きから ④印のある置き場所に古い端末が同期→書かない・知らせる ⑤知らせを押す→新しい置き場所で同期
- **実機では本物の置き場所で試さない。** 試しの置き場所を2つ作って（作ってもらって）確かめる
