## 質問1 根はどこに持つか・2台の合わせ方

### 推奨：`world/roots.json` 1ファイルに全部持つのは**反対**。根は「追記だけの記録」の並びにして、**調べたことの月ファイル（押した日の月）に相乗り**させる

記録の種類（案）：
- 根を立てた（名前・出発点の札・立てた人）／名前を直した／閉じた
- 札を根にぶら下げた（札の番号・根1〜2本・理由の短い文・札の fact の写し）／外した
- 今の答えを書き直した（根・どの答え①②③・文・当てた基準・根拠の札）
- 変えなかった（質問4）
- 予告がどの根の答えを確かめるか（質問7）
- まだ分からないこと を開いた／閉じた（質問8）

「今の根の姿」は、記録を日時順にたどって端末で組み立てる。記録は一度書いたら変えない（外す・閉じるは新しい記録）。

**なぜ**
1. 2台で同時に書いても**失わない**。記録は id ごとの足し合わせなので、朝の取り込み（iPhone）と読む回（PC）が同じ根に別々に枝を足しても両方残る。1ファイルで「根ごとに新しい方が丸ごと勝つ」形だと、片方の枝が消える
   - 近い実例（実測）：actors.json の札番号の合計が、9/12 00:40 の 107 から 08:26 の 99 に減っているコミットがある。主体は「新しい方が丸ごと勝つ」形。**原因が合わせ方かどうかは測れていない**（整理で減った可能性もある）
2. **古い版に落とされない**。世界の索引・主体・予告・札は知らない欄を落とす。dig の月ファイルは v20.48 で「知らない並びを残す」ようにしたばかりで、2台と古い版の試しも済んでいる
3. **ファイルが大きくならない**（質問3）。1ファイルだと中くらいの使い方で約100日で1MB を超え、多い使い方では1万日のうちに GitHub の1ファイル100MiB に届く（推測）
4. 世界の索引に何も足さない（v20.37 と同じ穴を作らない）

### 失うもの
- GitHub の上で「根の一覧」を1ファイルで読めない（記録を組み立てないと今の姿が分からない）
- dig の月ファイルが「調べたこと」だけの場所でなくなる（v20.47 の picks、v20.48 の imports に続いて3つ目の相乗り）
- dig は起動時に全部の月を持つので、**1万日後に記録の分だけ端末の持つ量が増える**（中くらいの使い方で約90MB 上乗せ。推測。言葉の全件読み込みと同じ種類の問題で、datalyou 報告の判断待ちと重なる）
- v20.47 以前の端末が月ファイルを書き直すと記録が消える（v20.48 以降の端末が持っていれば書き戻す。実測済みの動き）
- 2台で同時に同じ名前の根を立てると、別の番号の根が2本できる（組み立てるときに「同じ名前の根が2本」を出す必要がある）

### 別案（dig と分けたい場合）
`world/roots/` に同じ仕組み（月ファイル＋月の一覧）を新しく作る。古い版はこの場所を知らないので**一切触らない**（一番安全）。失うもの：同期の仕組みをもう1組持つ・同期のたびに GitHub の呼び出しが1回増える・2台と古い版の試しを一からやり直す。

## 質問2 札と根の紐づけは、札側か根側か

### 推奨：**どちらでもなく、紐づけ自体を記録にする**（質問1の「札を根にぶら下げた」記録）。札も根の定義も書き換えない

**札側に持つのは反対**（コードから・実測）
- 札を整えるとき知らない欄は落ちる。古い版の端末がその月のどれか1枚を触ると、**その月の全部の札から根の印が落ちた形で GitHub に書かれる**
- しかも、新しい版の端末は落ちたことに気づかない。送るか決める印が「id と updatedAt」だけなので、落ちた欄を書き戻しに行かない（手元には残る。**別の端末や入れ直した端末には戻らない**。コードから。動かしては確かめていない）
- 札に書くと、その札の eventDate の月ファイルを丸ごと書き直す。出発点の札は数ヶ月〜数年前の月なので、古い月のファイルが根の世話のたびに書き換わる
- 「既存の札を書き換えない」原則にも正面から当たる

**根側（roots.json の中の札番号の並び）も反対**
- 根ごとに新しい方が丸ごと勝つので、2台で同時に枝を足すと片方が消える（質問1）

### もう片方から引くのに要るもの
| 引き方 | 要るもの |
|---|---|
| 札 → 根 | 紐づけの記録を全部見て「札番号 → 根」の表を作る。dig は起動時に全部持っているので通信は要らない。v20.48 の「続報の前の札」と同じやり方（今は開くたびに全部見ている。1万日では表を1回作って持つ必要がある） |
| 根 → 札 | 同じ表の逆。札の中身を出すには札の月ファイルが要る。**札番号に eventDate が入っているので、索引なしで月が分かる**。ただし読み込んでいない月は GitHub から取る（出発点が古いほど取る月が増える） |
| 根の画面で一覧だけ出す | 紐づけの記録に「札の日付と fact（24字くらい）」を写しておけば、月を取らずに一覧が出る。開くときだけ月を取る |
| 1枚2本まで | 記録を日時順にたどり、3本目の記録は「根の切り方が粗いサイン」として数えるだけで効かせない |

### 失うもの
- 札のファイルだけ見ても、どの根か分からない
- fact の写しは、札の側が直っても古いまま（fact は今の作りで書き換わらないので、実害は小さい見込み）
- 紐づけ1件あたり約0.55KB（字下げ込み、写しと理由込み）。写しと理由をやめると約0.3KB

## 質問4 「変えなかった」の記録を残すか

### 推奨：**残す。1回の読む回で、その回に新しい枝が来た根だけ、根ごとに1行**（答えごとに3行にはしない）

- 中身：どの根・どの答えを見たか・変えなかった理由1行（40字）・見た札の番号・日時
- 置き場：質問1の月ごとの記録
- 画面：根の答えの横に「最後に書き直した日」とは別に**「最後に確かめた日」**を出し、変えなかった回は畳んで「変えなかった 5回（最後 9/20）▸」
- 新しい枝の来ていない根には書かせない（毎回10行の「変えなかった」は読み飛ばされる）

**なぜ残すか**
- 「見て変えなかった」と「見ていない」を分けられるのはこの記録だけ。質問22（開かなくても育つか）で、根が生きているかを**人が開かずに**判断する材料になる（例：60日確かめていない根は朝に1行）
- 変えなかった理由の文が並ぶと、「理由と行動のずれ」を見落としていないかを後で読める

### 失うもの
- 量：1万日で約4〜55MB（質問3の表、変えなかったの分）
- 読む回の返事が根の本数ぶん長くなる（1行40字×触った根）
- 「変えなかった」を返さない回（チャットが省いた）は、「見ていない」と区別がつかない。取り込みの結果に「根 8本のうち 6本に返事、2本は返事なし」と出す必要がある

### 反対案：残さない
失うもの：根が止まっているのか、見て変わらないのかが分からなくなる。3.4 の「黙って何も返さない形にしない」を、画面には出すがデータに残さない形になり、後で数えられない。

- 札との結びつきは弱い：地層に付いた札は多いが、値が入ったのは8点。「世界貿易/GDP」は20枚に付いて値0点で、概念の「チョークポイント」と同じ「広く付くが中身が無い」形になりかけている

### 推奨
- 根は地層を**参照するだけ**（「この根で見る地層」0〜3本）。地層を根に吸収しない、根を地層にしない
- 根の答えの根拠に数字を使うときは、地層の値（日付つき）を写す（予告の答え合わせの evidence と同じ考え方）

### 失うもの
- 「向き」を地層（dir）と根の答えの両方で書くことになり、食い違うことがある
- 見る地層を根ごとに選ぶ手間（割り直しのときチャットに書かせれば人の手間は無い）

## 質問7 予告に根を足すか、根から引くか

### 推奨：**予告のファイルには足さない。根から引く**。ただし「どの根の、どの答えを確かめる予告か」は、予告を作った読む回で**記録として1件足す**

- 引き方：予告の元の札（fromEventId、33本すべてにある。元の札は29枚）→ 紐づけの記録 → 根
- 予告に根の欄を足すのは反対（コードから・実例）
  - 予告を整えるとき知らない欄は落ちる
  - 予告は1本ごとに新しい方が丸ごと勝ち、結果を押すたびに updatedAt が変わるので、古い版の端末が結果を押すと根の欄が消える
  - 予告の変化の知らせは世界の索引頼みで、ここは v20.37 で3本消えた場所
- 元の札だけから引くと、1枚の札が根2本にぶら下がるとき、予告がどちらの答えを確かめているか決まらない。だから読む回で「予告 fc_… は 根 X の答え②を確かめる」を記録にする

### 失うもの
- 予告の画面から根を出すには、記録をたどる手間がかかる（端末の中なので通信は要らない）
- 今ある33本は「どの答えか」の記録が無い。元の札から根を引くだけになる（2本にぶら下がる札なら両方に出る）
- 札が後で別の根に付け替えられると、記録の無い予告は根の画面で出る場所が変わる
- 予告の元の推定（fromRead）のうち16本は60字で切れたまま（質問25）

|---|---|---|
| 誰が立てる | 本人が自分の言葉で | 読む回・調べた記録から出る |
| 形 | 大きな「なぜ」1文に、チャットの見立て全体 | 根の答えの穴1行（「攻撃したのはフーシ派かイラクの勢力か」） |
| 閉じるか | 閉じない（何度も投げる） | 分かったら閉じる |
| 答えの残し方 | 同じ日は置き換え | 追記（開いた・閉じた） |

### 推奨
- 別に持つ。名前も分ける：根の方は「**まだ分からないこと**」（調べた記録と同じ言葉）にして、「問い」と呼ばない
- 調べた記録の「まだ分からないこと」を、その札の根に**写せる**ようにする（論点5 と重なる。自動にするかは別に決める）
- 問い（asks）は根にしない・吸収しない。本人の問いが根の候補の種になることはあるが、それは根の候補の出し方（質問11）で扱う

### 失うもの
- 「問い」と名のつく場所が2つ残る（名前を分けて緩める）
- asks の「欲しいもの／恐れ／縛り」は根の答え①②に一番近い形だが、根には流れ込まない（2件なので実害は小さい）

## 質問19 出発点の札と「url が無いものは取り込まない」、古い eventDate の札

### 両立：**出発点も普通の札として、url のある出来事にする**（関税の「水準」のような状態ではなく、「2025年○月○日に米国が相互関税を発表」のような日付と出典のある動きにする）
- 取り込みは今も url が無い札を落とす（コードから）。出発点だけ例外にするのは反対（信頼の土台が崩れる）
- 状態（水準）は札でなく根の答えか地層に書く
- 日が分からない出発点は、v20.45 の「月まで」で作れる

### 古い eventDate の札を入れたとき（コードから。先例：問いから入った札8枚・初期投入45枚。今の132枚のうち**7枚が作った日より90日以上前の出来事、46枚が30日以上前**）
| どこ | どうなるか |
|---|---|
| 置き場 | **eventDate の月**のファイル（作った日の月ではない）。古い月のファイルが書き直される |
| 起動時 | 読む月は「今月と先月（30日前の月）＋未読のある月」。**読んだ後は古い月は起動時に読まれない**ので、世界の一覧に出ない（v20.45 報告で端末Bに出なかったのと同じ）。根の画面からは札番号で月を取れば開ける |
| 今日の札の並び | 作った日の順なので、その日の分として出る |
| 読む回 | 未読の中では eventDate の新しい順なので、**後ろに回る** |
| 地図（直近90日） | eventDate で数えるので、**90日より古い出発点は地図に一度も出ない**。小さな地図（7日）にも出ない。取り込みの結果に「90日より古い出来事 N件」と出る |
| 重複 | eventDate の前後3日（月までならその月）を、その月を読み込んでから見る。古い日付でも効く |
| すでにある札の一覧（same・follows 用） | 作った日で14日なので、作ってから14日間は一覧に載る |
| 最近のお金の動き（after 用） | eventDate で30日なので**載らない**。朝の取り込みで出発点を「前の動き」に指せない |
| 今日の3件 | 朝の取り込みの JSON に混ぜると選ばれうる。出発点は別のプロンプトで作るなら関係ない |
| 主体の時系列 | eventDate の位置に入る（ずれない） |

### 推奨
- 出発点は**朝の取り込みと別のプロンプト**で作る（今日の3件・same に混ぜない）
- 古い日付を入れてよい。ただし「根の出発点」は紐づけの記録の種類で見分け、根の画面から出す（一覧・地図に出ないのは受け入れる）

### 失うもの
- 出発点は世界の一覧・地図には出ない（根の画面からだけ）
- 古い月のファイルが書き直される（出発点10〜20枚なら一度きり）
- 出発点を「前の動き」として朝の札から指せない（紐づけの記録で根にぶら下げれば、根の画面では前後が見える）

## 質問25 データの傷を根より先に直すか

### 1) 60字で切れた推定（実測）
- 推定168件のうち**60字ちょうど135件**（札102枚、どれも「切れた推定を直した印」が無い）。60字未満10件・60字超23件。直した記録（切れていた読み）20件・札14枚
- 予告の元の推定も**16本が60字**（元の札のうち15枚が切れた札）
- **原因は v20.33〜36 で直した「切れる」と同じ**：v20.32 までは推定を保存するとき60字で切っていた。135件の読んだ時刻は全部 9/12 05時〜9/13 22時（世界時）で、v20.33 を出した 9/13 23:14（世界時）より前。それ以後に60字ちょうどの推定は増えていない
- 今残っているのは、切れた文を直す仕組み（読む回の枠5枚）が**少しずつしか回らない**ため。今の待ち：切れた102・朝の浅い読み3・未読5 → 1回の読む回で切れた札は約12枚（枠5＋余り7）→ 新しい札が来なければ**約9回**、毎日10枚ずつ来るなら10〜20回（推測）

**推奨：割り直し（どの根か）の前には直さなくてよい。初めの「今の答え」を作る前には直す**
- どの根の枝かは、何が起きたか・なぜ・お金の動き・した事で決まる。推定は要らない（割り直しに推定を渡さない、または「60字で途中まで」と印を付けて渡す）
- 答え②（誰に向けた手か）は推定が材料。切れたまま答えを作ると、切れた文から答えが育つ
- 早く直すなら、一時的に切れた札の枠を20枚にして読む回を約5〜6回（102÷20）
- 失うもの：読む回5〜6回ぶんのチャット時間。**直し方は「切れた文を別の欄に移して、推定の文を入れ替える」なので、厳密な「追記のみ」ではない**（v20.35 で決めた形。前の文は消えない）

### 2) 同じ出来事で食い違う札
- 評価報告書の振り分けで重複・続報32枚（24%）。サウジのパイプライン停止は3枚で、攻撃した側が「フーシ派」「イラクから飛来したドローン」「犯行声明なし」と食い違う
- 追記のみで直せる：札を消さず、**「同じ出来事の組」の記録を足す**（v20.48 の same と同じ形を、既存の札どうしに使う）。どれを代表にするかも記録
- 攻撃した側の食い違いは、直すより**その根の「まだ分からないこと」に入れる**方が筋が良い（どちらが正しいか、札の中の材料では決まらない）

**推奨：先に直さず、割り直しと同じ回でやる**
- 2回の割り直しで、同じ出来事の札が別の根に割られると「食い違い」に数えられて人が見る枚数が増える。割り直しのプロンプトに「同じ出来事の組」も書かせ、2回とも同じ組になったものだけ記録する
- 失うもの：割り直しのプロンプトと返事が長くなる。重複を畳まないまま根の枝の枚数を数えると多めに出る

### 3) 日付が逆の「前の動き」（実測）
- 前の動きの印は6枚。**日付が後の札を指すもの2枚**（Micron 6/25 → Alphabet 7/23、インド 8/27 → 中国 9/6）、同じ日の同じ出来事を指すもの3枚（中国の金・カナダの報復関税×2）
- 原因（コードから）：取り込みで前の動きを確かめるとき、相手が「お金の動きを持つ札か」だけ見て、**日付の前後を見ていない**
- **推奨：データは直さず、表示の決まりで扱う**（日付が後の札を指す印は「前の動き」として出さない）。取り込みにも日付の確かめを足す。根とは独立していつでもできる
- 失うもの：2枚の印は画面から見えなくなる（データには残る）

## 足りない論点（足した）

1. **「根」という言葉がもう使われている**：地図の「自分に使う金」の線を、主体の国に描く「根」と呼んでいる（v20.24〜27）。画面の文言が「イランの根（3本・自分に使う金・直近90日）」のように出る。器の「根」を入れると同じ画面に2つの意味が並ぶ。どちらかの呼び名を変えるか決めてほしい
