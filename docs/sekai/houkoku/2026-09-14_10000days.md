# 1万日耐えるデータ設計はあり得るか

日付：2026-09-14　元の指示書：`shiji/shiji_10000days_2026-09-14.md`（調べるだけ）
前の報告：[データ量](2026-09-14_datalyou.md)・[置き場所](2026-09-14_database.md)
**直していない。** kotoba-data の履歴を手元に複製して読むだけで測り直し（5,228コミット）、公式の資料を読んだ。

---

## 答え（先に）

**「1万日（27年）のあいだ、人が一度も手で直さなくて済む作り」は、あり得ません。**

- リポジトリの大きさだけに限っても、1GB 未満に27年収まると**言い切れない**（下の見込みは幅が大きく、保証できない）
- それより確実に、**データの作りと関係ない所で人の手が要る**：
  - GitHub の API の版は、新しい版が出てから「少なくとも24か月」だけ前の版を支える（公式の資料）。このアプリは版を指定しておらず、既定の版（2022-11-28）を使っている。27年のうちに版が変われば、アプリを直す必要がある
  - iPhone・Safari・ホーム画面のアプリの扱い、GitHub の決まり（1GB の目安・無料の範囲・鍵の決まり）が27年変わらない保証は無い
- 人が触らずに1GB を越える方法は1つだけある：**古い履歴を自動で消して詰める**。これは「全部の版が残る」を捨てることになり、**反対**

**それでも、手作業は小さく・まれにできる。** 測り直すと、履歴を大きくしているのは中身より「書く回数」だった（下）。書き方を直せば、**リポジトリを分ける手作業が27年で0回か1回で済む見込みがある**（保証はできない）。分けることになっても、**1回15〜40分の手順**にできる。

**勧める案：案B に「履歴を増やさない書き方」と「置き場所の名前を設定で変えられるようにしておく」を足して進める（案2）。**

## 1. ほかのシステムのやり方で、このアプリに当てはまるもの

| やり方 | よくある使われ方 | このアプリで | 理由 |
|---|---|---|---|
| **日付で分けて持つ** | ログ・時系列のデータを月や日で分ける | **使える（もう使っている）** | 言葉・日誌・札は月ファイル、瞑想は年ファイル |
| **索引だけ先に見る** | 全部を読まず、目次で必要な所を決める | **使える（一部使っている）** | 言葉・日誌・世界に索引がある。読む欄はまだ使っていない（前の報告の案B1・B2） |
| **古いデータは書き換えない（確定させる）** | 過ぎた期間を「読むだけ」にし、書くのは今の期間だけ | **条件つきで使える** | 札は読む回・切れた推定・予告で古い月も書き直す。**書き換える印を札と別のファイルに出せば**、古い月の札はほぼ書き換わらなくなる |
| **書く回数を減らす（まとめて1回）** | 変わった所だけを、まとめて1回で書く | **使える** | 変わらないファイルを書かない（案B6）。GitHub の API で、複数のファイルを1つのコミットにまとめることもできる（公式の資料：ファイルの中身・フォルダの一覧・コミットを作る窓口がある）。ただし呼ぶ窓口が増え、途中で失敗したときの扱いが要る |
| **古いデータを別の場所に移す（アーカイブ）** | 古い期間を安い置き場所へ | **使えるが人の手が要る** | 新しいリポジトリを作る・鍵に権限を足すのは人（下の 3） |
| **履歴を詰める（スナップショットだけ残す）** | 変更の記録を定期的にまとめて消す | **使えない（反対）** | 全部の版が残る、を捨てる |
| **追記だけのログ（変更を足していくだけ）** | 変更の積み重ねから今の状態を作る | **使えない** | 同期・合わせ方を全部作り直す。今の状態を作るのに、全部のログを読む（読む量の問題が戻る） |
| **大きなファイル用の置き場所（Git LFS）** | 大きな画像・動画 | **使えない** | このアプリのファイルは文字で、大きくない。LFS の容量は別の決まり。今の読み書きの窓口から使えない |
| **データベース・オブジェクトストレージ** | 大きなデータを必要な分だけ | 前の報告で勧めなかった | 版の履歴・アカウント・費用・止まったとき（前の報告） |
| **複数の場所に写す** | 同じデータを別々の所に持つ | **使える** | GitHub のほかに、手元の複製（`git clone`）を持つ。自動にするなら GitHub Actions（無料の個人アカウントの非公開リポジトリで月2,000分、公式の資料）で別の場所に写す手もあるが、仕組みが1つ増える |

## 2. 1万日後に手作業が要らない形はあるか

### リポジトリが1GB を超える問題を、人が触らずに越える方法

| 方法 | 人の手 | 捨てるもの | 今の作りのまま？ |
|---|---|---|---|
| **A 大きくならないように書く**（変わらないファイルを書かない・まとめて1コミット・書き換える印を別のファイルに） | 要らない | 無し（作り直しの手間だけ） | **できる** |
| B 1GB を超えても放っておく | 要らない | GitHub の「理想は1GB 未満、5GB 未満を強く推奨」を超える。**超えても止まる決まりは公式の資料に無い**が、GitHub から連絡が来ることがある | できる |
| C 古い履歴を自動で詰める | 要らない | **全部の版の履歴** | できる（反対） |
| D アプリが自分で新しいリポジトリを作って移る | 要らない | 鍵に「リポジトリを作る」権限を足す（鍵を盗まれたときの被害が広がる） | できる |

**A でどこまで持つか（見込み。幅が大きい）：**

| 書き方 | 1日の伸び（見込み） | 1万日後 |
|---|---|---|
| 今のまま | 約0.2〜0.6MB（実測） | 約2〜6GB |
| data.json・training.json を変わらなければ書かない | 約半分 | 約1〜3GB |
| さらに、1回の同期を1コミットにまとめる・印を別のファイルに | 中身の増えに近づく | **数百MB〜1GB 台**（言い切れない） |

- 最後の行の根拠：中身だけなら、言葉と札の文字は1日数十KB 増え、git で詰めるとさらに小さくなる。ただし、ファイルが大きくなったときの書き直しの詰まり方・言葉のつながりの書き換え・使い方の変化（本を数千枚）は**測れない**
- **「1GB 未満に27年」は言い切れない。「5GB 未満（強く推奨の範囲）に収まる」見込みは高い**（ただし保証はしない）

### 今の作り（1ファイル・ビルド無し・自分のサーバー無し）のままで可能か

- A・B・C・D は、どれも今の作りのまま作れる（画面から GitHub の API を呼ぶだけ）
- **無理なのは「27年間まったく人が触らない」こと**で、それは作りの問題ではなく、外の決まり（API の版・iPhone・GitHub の方針）が変わるため

## 3. 「手作業が要る」のは本当に悪いことか

### リポジトリを分ける手作業（必要になった場合）

今は仕組みが無いので、先に「設定で置き場所の名前を変えられる」「新しい置き場所へ今のファイルを写すボタン」を作っておく前提。

| 手順 | 誰が | 時間（見込み） |
|---|---|---|
| 1. GitHub で新しい非公開のリポジトリを作る（例 `kotoba-data-2`） | 人 | 約2分 |
| 2. 同期の鍵（Fine-grained トークン）の対象に新しいリポジトリを足し、Contents: Read and write を付ける | 人 | 約3分 |
| 3. アプリの設定で新しい置き場所の名前を入れ、［新しい置き場所へ写す］を押す | 人が押す・アプリが写す | 数分〜数十分（その時のファイルの数と大きさによる。**測れません**） |
| 4. もう1台の端末でも設定を変える | 人 | 約2分 |
| 5. 古いリポジトリを「アーカイブ（読むだけ）」にする | 人 | 約1分 |

- **合わせて15〜40分ほど**（3 の時間は測れない）
- **失敗したら：** 古いリポジトリは消さないので、データは失わない。写し終わる前に止まったら、設定を古い名前に戻してやり直す。**危ないのは、片方の端末だけ新しい置き場所に書き、もう片方が古い置き場所に書き続けること**（今日まで何度も起きた「片方の端末だけ」と同じ形）。写した後に、古い置き場所への書き込みを止める決まりが要る
- 過去の版を見るには、古いリポジトリも読む（アプリで古い年の札を見るなら、読み先を2つ持つ作りが要る）

### 仕組みで減らせるか

| 仕組み | 減る手間 |
|---|---|
| 設定に「今のリポジトリの大きさ」を出す（GitHub の API で取れる）。800MB を超えたら同期の1行に出す | 時期に気づく |
| 手順を kotoba-data の README に書いておく | 何年後でも手順が分かる |
| ［新しい置き場所へ写す］ボタン | 手順3が押すだけ |
| 古い置き場所への書き込みを止める印を、古いリポジトリに置く | 片方の端末だけ古い所に書く事故 |

### ほかの手作業と比べて、どちらが重いか

| 手作業 | 回数 | 1回の重さ |
|---|---|---|
| リポジトリを分ける（案B・案2） | 27年で0〜数回 | 15〜40分 |
| データベースを使う場合の、控えの書き出し・止まらないように使う・規約と料金を追う（前の報告） | 毎週〜毎月 | 数分〜 |
| 同期の鍵の入れ替え | Fine-grained トークンは期限なしも作れる（公式の資料。ただし組織の決まりで止められる場合あり）。期限を付けたなら、その度に | 数分 |
| 古い履歴を詰める（自動なら0回） | — | 手間は0だが、版の履歴を失う |
| **アプリを外の変化に合わせて直す**（API の版・iPhone の変化） | **27年で何回か（避けられない）** | 分からない |

**リポジトリを分ける手作業は、ほかの手作業より軽く、まれ。** 「手作業が要る」こと自体より、**時期に気づけないこと・手順を忘れること・片方の端末だけ古い所に書くこと**の方が危ない。これは仕組みで減らせる。

## 4. 27年のあいだに変わること

| 変わりうること | 起きたら | 備え |
|---|---|---|
| GitHub の 1GB の目安・無料の範囲が変わる | 厳しくなれば分ける時期が早まる。有料になる可能性 | 大きさを画面に出す。分ける手順を作っておく |
| GitHub の API の版が変わる | 新しい版が出てから少なくとも24か月は前の版が使える（公式の資料）。その間にアプリを直す | 版を明示し、知らせを追う（人の手） |
| GitHub が無くなる・使えなくなる | 端末と手元の複製にデータが残る。**git は GitHub が無くても読める** | 手元の複製（`git clone`）を持つ。GitHub 以外の git の置き場所にも写せる |
| iPhone・Safari でホーム画面のアプリの扱いが変わる | アプリが開けなくなる可能性。**データは GitHub と手元の複製に残る** | データをアプリに頼らず読める形にしておく |
| 自分の GitHub アカウントに入れなくなる | 最悪、データに届かない | 手元の複製、別の場所への写し |

### 一番変わりにくい置き方

**文字だけの JSON（UTF-8）を、git の履歴つきで、2か所以上に置く。**
- JSON は RFC 8259（インターネットの正式な標準 STD 90）。UTF-8 で書くことが決まっている（公式の資料）。特定のアプリ・サービスに頼らず、文字として読める
- git は GitHub が無くても動く。複製に全部の版が入る
- 今の kotoba-data はすでにこの形。**変えない方がよい**

### 27年後もデータを読めるか

- **読める見込みが高い。** JSON は文字なので、アプリが無くても中身は読める。依存しているのは JSON と UTF-8 と git だけ
- **読めなくなりやすいのは「意味」**：`readBy: "yomu"`・`cutFixAt`・`verdictFact: "late"` などの欄が何を意味するかは、今はアプリのコードとこの報告書の中にしか無い。**欄の意味を kotoba-data の中に書いておかないと、27年後にアプリのコードが読めないと意味が分からない**

## 5. 今決めておくべきこと・決めなくてよいこと

### 今決めておくと後で楽になること

| 決めること | なぜ今 | 失うもの |
|---|---|---|
| **中身が変わらなければ書かない**（data.json・training.json・索引） | 今の履歴の半分近く。後から減らせない（履歴は残る） | 無し |
| **書き換える印は、札と別のファイルに置く**（前の報告の月ごとの印ファイル） | 印を足す前に決めないと、後で移し替えが要る | ファイルが1種類増える |
| **置き場所（リポジトリ）の名前を設定で変えられるようにする**（今はコードに固定） | 分ける時が来たときに、コードを直さずに済む | 設定が1つ増える |
| **欄の意味を kotoba-data の README に書く** | 27年後にアプリ無しでも読める | 欄を足すたびに書く手間 |
| **手元の複製を持つ** | GitHub が使えなくなったときの控え | 置き場所の容量（今は数MB） |

### 今決めなくてよいこと

- いつリポジトリを分けるか（大きさを見てから）
- 1回の同期を1コミットにまとめるか（書く回数を減らした効きを見てから）
- 古い年のデータを別のリポジトリに移すか、放っておくか
- データベースに移すか（前の報告で勧めなかった。案B で足りないと分かってから）
- 履歴を詰めるか（反対。決めないまま）

### 案B を進めながら、後から選べる余地を残せるか

**残せる。** 案B はデータの形を大きく変えない（読み方と分け方）。上の「今決めておくこと」を足しても、後から「分ける」「まとめて1コミット」「データベース」のどれも選べる。**選べなくなるのは、履歴を詰めた場合だけ**（消した版は戻らない）。

## 案を並べる

| 案 | 中身 | 人の手（27年） | 捨てるもの |
|---|---|---|---|
| **1 案B のまま進める** | 前の報告の B1〜B7 | リポジトリを分ける：約2,000〜数千日で1回以上（今の書き方の伸びなら）。外の変化に合わせた直し | 無し（ただし履歴が今のペースで伸びる） |
| **2 案B＋履歴を増やさない書き方＋置き場所の名前を設定に（勧める）** | 案B に、変わらなければ書かない・印を別ファイル・置き場所の名前を設定に・欄の意味を README・大きさを画面に | リポジトリを分ける：0〜1回の見込み（言い切れない）。外の変化に合わせた直し | 無し（作る手間が少し増える） |
| 3 古い履歴を自動で詰める | 年ごとの控えだけ残し、履歴を消す | 分ける手間は0 | **全部の版の履歴**（反対） |
| 4 アプリが自分で新しいリポジトリを作る | 鍵に「リポジトリを作る」権限 | 分ける手間はほぼ0 | 鍵の安全（盗まれたときの被害が全部のリポジトリに広がる）。条件つきで反対 |
| 5 データベースに移す | 前の報告の案C・D | 毎週〜毎月の控え・監視 | 版の履歴・費用・止まる心配（前の報告） |

### 勧める：案2

- 27年間まったく人が触らない形は無い。だから「**手作業を小さく・まれに・迷わずに**」を狙う
- 測り直すと、履歴を大きくしているのは**中身ではなく書く回数**だった。書く回数を減らすのは、失うものが無く、**今やらないと後から取り戻せない**（すでに書いた履歴は減らない）
- 置き場所の名前を設定にしておけば、分ける日が来ても手順は15〜40分で、データは失わない
- 全部の版の履歴・無料・サーバー無し・今の作りを守れる
- 後から選べる余地が一番広い

**反対：** 案3（版の履歴を捨てる）。案4 は鍵の安全を下げるので、分ける手間（15〜40分）と比べて割に合わない。

## 分からないもの・測れないもの

- 書き方を直した後の履歴の伸び（見込みは幅が大きい）
- 27年のあいだの GitHub・iPhone・Safari の決まりの変化
- ［新しい置き場所へ写す］にかかる時間（その時の大きさによる）
- 本を数千枚入れるなど、使い方が変わったときの伸び

## 確かめた資料（2026-09-14）

- GitHub：大きなファイル（1ファイル100MiB、リポジトリは理想1GB 未満・5GB 未満を強く推奨）
- GitHub：個人の鍵（Fine-grained トークンは期限なしも作れるが組織の決まりで止められる場合あり。クラシックの鍵は1年使わないと自動で消える）
- GitHub：REST API の版（新しい版が出てから少なくとも24か月は前の版を支える。版の指定が無いと 2022-11-28 を使う）
- GitHub：Git のコミットを作る窓口（ファイルの中身・フォルダの一覧・コミットを別々に作れる）
- GitHub：Actions の無料の範囲（個人の無料アカウントの非公開リポジトリで月2,000分）
