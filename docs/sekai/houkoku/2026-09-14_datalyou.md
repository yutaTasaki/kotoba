## 3. どこが先に壊れるか

### 3.1 読む欄を開くと、全部の月を GitHub から取り直す（一番先）

**作り（コードで確かめた）：**
- 読む欄を描くとき、索引にある月のうち、この起動でまだ読み込んでいない月を**全部同時に**読み込む（v20.35）
- 月の読み込みは、端末の保存場所から読んだ後、**必ず GitHub から同じ月を取って合わせる**（端末に最新の分があっても取る）。起動し直すと、読み込んだ印が消えるので、**開くたびに全部の月をもう一度取る**
- 同時に取る数に上限が無い

**大きさと時間（見込み。札 10枚/日）：**

| | 今 | 200日後 | 1,000日後 | 3,000日後 | 1万日後 |
|---|---|---|---|---|---|
| 月の数（出来事の日付の月） | 11 | 約18 | 約44 | 約110 | 約340 |
| 1回に取る量（GitHub の返事は Base64 で約1.37倍） | 約0.6MB | 約10MB | 約50MB | 約150MB | 約500MB |
| この PC の速さ（1ファイル0.3〜0.8MB/秒）で1本ずつなら | 1〜2秒 | 十数〜30秒 | 1〜3分 | 数分 | 10分以上 |
| 全部の札をメモリに置く（この PC で整えた後の大きさ） | 1MB 未満 | 約7MB | 約34MB | 約100MB | 約340MB |

- **何が壊れるか：** まず毎朝の取り込みの画面が開くたびに遅くなる（約200日後から）。月が100を超えるころ（約3,000日後。古い日付の札が入ると早まる）、GitHub の決まり（公式の資料：同時の呼び出しは100まで、1分に900点まで、1時間に5,000回まで）の「同時に100まで」を超え、呼び出しが断られうる（断られた月は端末の分だけで出るが、同期のエラーが出る）。数千日後には全部の札をメモリに置くことで、iPhone で画面が落ちるおそれ（**どこで落ちるかは測れません**）
- 通信の速さはこの PC で測った値。iPhone・携帯回線での速さは**測れません**。同時に取るので1本ずつより速い可能性もある

### 3.2 起動のたびに、全部の言葉を読んで持つ

**作り：** 言葉は起動時に端末の保存場所から**全部の月**を読んでメモリに置く（網・相談・関連づけが全部の言葉を使うため）。通信はしない。

**本物の言葉を複製して、この PC で測った（読み込み＋整える）：**

| | 件数 | JSON の大きさ | 時間 | メモリ |
|---|---|---|---|---|
| 今 | 173 | 0.4MB | 1ミリ秒 | 1MB |
| 1,000日×5件/日 | 5,000 | 9MB | 31ミリ秒 | 19MB |
| 1万日×5件/日 | 5万 | 93MB | 334ミリ秒 | 189MB |
| 1万日×17件/日 | 17万 | 316MB | 1.1秒 | 642MB |

- iPhone での時間とメモリの上限は**測れません**（PC より遅く、1つの画面が使えるメモリも小さい）
- **何が壊れるか：** 起動が遅くなり、メモリが足りなくなると iPhone で画面が落ちる。1日17件のままなら数千日のうちに数百MB になる

### 3.3 本を数千枚入れる場合

| 入れ方 | 起きること |
|---|---|
| 数千枚を**1か月の間**に入れる（例 3,000枚） | その月の言葉のファイルが約12MB。**言葉を1件保存するたびに、その月のファイル丸ごと（Base64 で約16MB）を GitHub に送る**。1件ごとに数十秒かかる見込み（送る速さは**測れません**） |
| 同じく、関連づけの費用 | 1件約0.012ドル（今月の実測）×3,000件＝**約36ドル**。月の上限10ドルに3か月以上かかる（上限で止まる） |
| 数千枚を何年かに分けて入れる | 月ファイルは小さいまま。メモリ（3.2）に効くだけ |

- 本の枚数・入れる速さは決まっていないので、ここは**条件ごとの見込み**

### 3.4 1つのファイルに増え続けるもの

| ファイル | 1万日後 | 起きること |
|---|---|---|
| 予告（5本/日） | 約50MB | GitHub の警告（50MiB）の手前。**押すたびに丸ごと書き直す**ので、数MB を超えたあたり（約1,000日後）から押すたびの送信が重い |
| 概念・主体・用語 | 15MB・7〜24MB・数MB | 起動時に全部読む。取り込むたびに丸ごと書き直す |
| 数字（端末の中） | 約58MB | 端末では全部の月を1つの置き場所にまとめ、古い月を消さない。貯めるたびに全部を書き直す |
| 筋トレ | 約4MB | 1回の記録ごとに丸ごと書き直す |

- **GitHub の 100MiB には、今のペースでは1万日のうちに当たらない**
- ファイルを書く GitHub の窓口（PUT）の大きさの上限は、公式の資料に書かれておらず**測れません**

### 3.5 リポジトリの大きさ・コミットの数

- GitHub の目安：リポジトリは「理想は1GB 未満、5GB 未満を強く推奨」。超えると GitHub から連絡が来ることがある（公式の資料）
- 履歴の増え方1日約0.5MB が続くと、**約2,000日で1GB、約1万日で5GB 前後**。ファイルが大きくなるほど1回の書き直しが大きくなるので、実際はもっと早い可能性がある（**幅が大きい。測れない部分**）
- コミットは1日約650（8日で5,226）。**data.json と training.json を同期のたびに書いている**のが大半（1.8）。1万日で数百万コミットになる。GitHub にコミット数の決まった上限は無いが、履歴が重くなる

### 3.6 iPhone の保存できる量

- 公式の資料（WebKit）：Safari 17 以降、1つのサイトが使えるのは**端末の容量の最大60%**。ホーム画面に置いたアプリも同じ
- 1万日後に端末に置く量は、多い場合で言葉 数百MB＋読んだ札 数百MB＋数字 約60MB で、**1GB 前後**。128GB の iPhone なら上限（約77GB）に遠い
- **注意：** 保存は「最善を尽くす」扱いで、端末の空きが無くなると使っていない順に消されうる。消さないで、と頼む設定（persistent）をこのアプリはしていない。GitHub に同期済みの分は消えない

### 3.7 画面が開くまでの時間

- 起動時に読むもの：言葉の全部の月、日誌の今月と先月、瞑想の全部の年、世界の今月と先月と未読のある月、概念・用語・主体・地層・予告・聞いたこと・出典の各1ファイル
- 今の iPhone での時間は**測れません**。この PC での読み込み＋整えるの時間は、言葉と札を合わせて今は数ミリ秒、1万日後に言葉5件/日なら約0.3秒＋概念などの大きなファイル
- 1万日後の iPhone での時間は**測れません**

### 3.8 同期にかかる時間

- 普段の同期は、変わった月だけを取りに行く（言葉・日誌・札とも、索引の日時で見る）。**月が増えても、普段の同期は重くならない**
- 重くなるのは 3.1（読む欄）と 3.4（丸ごと書き直すファイル）

### 3.9 プロンプト

- 取り込む回：知っている概念は最近の120件、主体は60件で打ち切り。地層は20系列。**伸び続けない**（主体が60件を超えると、古い主体は一覧から外れ、同じ主体を別の名前で作るおそれが増える）
- 読む回：1回20枚。朝の言葉：言葉が200件を超えると、全部ではなく候補だけを渡す
- **プロンプトの字数で壊れる所は無い**

| 読む欄を開くたびの通信（3.1） | 1万日後に約6MB 増える |

### 何個までなら問題ないか

- **個数では先に困らない。** 読んだ・理解度・深掘り度・重みの4つを全部日時つきで足しても、札の月ファイルが約5%大きくなるだけ
- **困るのは置き方：**
  1. 札の中に入れると、**印を押すたびに、その月の札のファイル丸ごと**（1万日後には1か月約1MB、Base64 で約1.5MB）を GitHub に書き直す。履歴もその分増える
  2. 札を整える決まりは、知らない欄を落とす（古い版の端末が印を消す。今日まで何度も起きた形）
  3. 読む欄の全部の月の取り直し（3.1）が、印の分だけ重くなる

### 札の中より良い置き方

| 置き方 | 良い所 | 失うもの |
|---|---|---|
| 札の中 | 作りが一番簡単 | 上の1〜3 |
| **月ごとの印だけのファイル**（`world/marks/YYYY-MM.json`、札の番号→印） | 印を押しても小さいファイルだけ書き直す。札のファイルと別なので、古い版の端末が札を整えても印は消えない | ファイルが1種類増え、同期と合わせ方を作る必要がある。印を見るときに札と組み合わせる |
| 印を全部1ファイル | 作りが簡単 | 1ファイルが増え続ける（3.4 と同じ問題） |

**勧める：月ごとの印だけのファイル**（出来事の日付の月で分ける）。

## 5. 直し方の案（この段では直さない）

| 案 | 中身 | 効く所 | 失うもの |
|---|---|---|---|
| **0 直さない** | 今のまま | — | 約200日後から読む欄が遅くなる。本を1か月に数千枚入れると保存が重い。data.json・training.json のコミットが増え続ける |
| **1 読む欄で、端末にある月は GitHub に取りに行かない** | ふだんの同期と同じく、索引の日時が変わった月だけ取る | 3.1 の通信がほぼ無くなる | ほかの端末が古い月を直したとき、次の同期まで反映が遅れる（ふだんの同期で拾う） |
| 2 読む枠の候補を、索引で先に絞る | 未読・切れた推定・予告の元の札がある月だけ読み込む（索引に月ごとの数を持つ） | 3.1 のメモリも減る | 索引の作りが増える。数え方がずれると、読むべき札が出ない |
| 3 古い月は読む枠に出さない | 例：出来事の日付が直近24か月の札だけ | 3.1 が頭打ち | 古い札の読み直し・古い日付の予告の元の札が出ない |
| **4 中身が変わらなければ data.json・training.json を書かない** | 合わせた結果が同じなら送らない | 3.5 のコミットが大きく減る | 無し（書く・書かないの判定を足すだけ） |
| 5 増え続ける1ファイルを分ける | 予告を年ごと、概念の「この札に出てきた」を札の月ファイル側から数え直す、数字は端末でも月ごとに置く | 3.4 | 作り直しが大きい。移すときにデータを失う危険がある。1,000日までは急がない |
| 6 言葉を起動時に全部読まない | 最近の月だけ読み、網・相談は必要なときに読む | 3.2 | 網・相談・関連づけの作りを変える必要がある。大きい |
| 7 本の取り込みを別の置き場所に | 本の言葉は本ごとのファイルにする | 3.3 | 言葉の一覧・網・関連づけとのつながりを作り直す |
| 8 消さないで、と頼む（persistent） | 端末の保存が消されにくくなる | 3.6 | iPhone でどう効くか**測れません** |

**勧める順：** 1 と 4 を先に（小さい直しで効きが大きい）。本を数千枚入れる前に 7 か「1か月に入れる枚数の上限」を決める。2・3 は約1年以内に決める。5・6 は1,000日を超える前に。印は、足すときに**月ごとの印だけのファイル**で。

## 6. 測れないもの

- iPhone での起動時間・メモリの上限（どこで画面が落ちるか）
- iPhone・携帯回線での GitHub の速さ
- 端末に今保存している量（設定の「統計と使用量」で見られる）
- GitHub がファイルを書く窓口で受け付ける大きさの上限（公式の資料に無い）
- これからの使い方：言葉を1日何件入れるか（今は8日しか測っていない）、本を何枚・どの速さで入れるか、札を1日何枚入れるか、読む回を毎日流すか
- 9/7 より前の履歴（リポジトリの履歴がそこから）
- リポジトリの大きさの伸び（ファイルが大きくなると1回の書き直しが大きくなるので、1日0.5MB より早くなりうる）

## 何を含めて測ったか

- kotoba-data：今の版の全ファイル（旧・年ファイルと捨てる前の控えを含む）。散歩（walk10000-data）は別に表示
- 1件あたりの大きさ：ファイルの大きさ÷件数（字下げ込み）と、字下げを外した JSON の字数
- 増え方：各件の「作った日時」（日本時間の日付）。札は世界を作り直した 9/11 以降、初期投入の印がある札を分けた
- 読み込みの時間とメモリ：本物の言葉173件・札（9月の64枚）を番号だけ変えて複製し、本物の整える処理（言葉の月・札の月）を通した。この PC の Node で、JSON を読む時間＋整える時間、メモリは整えた後に持っている分
- 通信の速さ：この PC から GitHub の窓口で、札の9月（約32万バイト）・言葉の9月（約93万バイト）・地層（約29万バイト）を2回ずつ取った時間
- 履歴の増え方：日ごとに、その日のコミットに含まれる git の物の、詰めた後の大きさの合計（前の日から変わっていない物も含むので多め）
