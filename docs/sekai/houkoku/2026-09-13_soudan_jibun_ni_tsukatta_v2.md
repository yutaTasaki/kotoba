1. **困っていることは正しいが、「場所不明を自分に使ったに改名する」のには反対。** 自分に使った金の札は16枚あるが、場所不明に落ちているのは**6枚だけ**。残り10枚（Amazon・Microsoft・NVIDIA の設備投資、トヨタの自社株買い、メキシコのペメックス支援など）は、すでに「国内」や「市場への線」として地図に乗っている。一方、場所不明の11件のうち**5件は自分に使った金ではない**（原油・LNGの輸入代金、通航料、金の買い入れ、石油在庫）。改名すると、5件を誤って呼び、10件を取りこぼす
2. **「自分に使った」は場所ではなく「使い道」。** 場所（どこからどこへ）とは別の軸として、全部の動きに付けるのがよい。判定は札の「何の支払いか」の欄の言葉で**90日分86本のうち16本を拾え、明らかな誤りは0本**だった

4. **積み上げは、いまは作らないほうがよい。** 期間がばらばら（四半期・半年・1年・年の計画）で、同じ出来事が複数の札になっている（トヨタは同じ日に5枚）。札のまま足すと、トヨタだけで約10.3兆円になり、実際（実績3.66兆円＋枠1兆円）の約2.2倍になる

## 1. この案そのものをどう思うか

**推奨：** 問題の捉え方（重要な札が「その他」に沈んでいる）には賛成。直し方は変える。

- 「場所不明」は**場所の直し**で減らす（第1段。場所不明 9件→4件になると試算）
- 「自分に使った」は**使い道の印**として、場所とは別に全部の動きに付ける（第2段）
- 地図では、いまある種類の絞り（全部・お金・物と人・原油と石油・約束）に**「自分に使う」を1つ足す**。押すと、場所不明に落ちたものも国内に入ったものも、同じ1か所で見える

**理由：**

- 実測で、自分に使った金16枚の居場所は「場所不明6・国内6・市場への線4」に割れている。場所不明の箱だけを改名しても、「誰が自分に賭けているか」の半分以上が見えない
- 同じ「設備投資」でも、Amazon・Microsoft・NVIDIA は国内、TSMC・Alphabet は場所不明、と**相手の言い方の違いだけで**分かれている。これは場所の振り分けのほうの不揃いで、名前を変えても直らない
- 場所不明の11件のうち、相談書の「主体の国は分かっていて、相手が設備・市場・自分」に当たるのは4〜6件。残りは本当に相手の国が言い切れないもの

**他の選択肢：**

- 案のとおり改名＋根：上の理由で、誤りと取りこぼしが出る
- 場所不明を地図の下にボタンではなく**札の見出しとして並べる**（「放っておいたら見ない」への直接の手当て）。第1段のあと4件ほどなら並べても邪魔にならない。これは使い道の印とは独立にやれる

**やった場合に失うもの（推奨案）：**

- 「外に出す金」と「自分に沈める金」を**同じ地図の同じ画面で同時に**見る、という形は諦めることになる（絞りを切り替えて見る形になる）
- 使い道の判定は言葉の一覧に頼るので、生成が新しい言い方をしたら拾い漏れる。一覧を足し続ける手間が残る

## 2. 「自分に使った」をどう判定するか

**実測（相談時点＝9/12 13:39 のデータで、画面の11件を再現できた）：**

## 3. 根を描くのは、いまの地図の作りで無理がないか

**推奨：** 根は描かない。地図に印を出すなら、点の**周りの輪**（太さはドル換算の5段）にとどめる。第2段の「自分に使う」の絞りだけで足りるなら、輪も要らない。

**理由（実測）：** 根の長さを20px、押せる幅を左右11pxとして、実際の地図の点の位置で測った。

| 国 | 幅360 | 幅320 |
|---|---|---|
| 日本 | **台湾の点を突き抜ける**（下15.6px） | 同じ（下13.9px） |
| サウジ | **カタール・UAE・イエメン・エチオピアに重なる** | 同じ |
| 米国 | メキシコの点にかかる | 同じ |
| 台湾・中国・カナダ | ぶつからない | ぶつからない |

- 日本（トヨタの自社株買い）と台湾（TSMC）は、相談の一番の例どうしがぶつかる
- **向きの問題：** いま、市場・国際機関・地域の枠へ向かう線は、地図の下の箱へ向かって**下に伸びる**。根も下に伸びると、「市場への線」と「自分に沈めた金」が同じ向きになり、形で見分けられない
- 描くこと自体はできる：線と点は拡大のたびに描き直していて太さは変わらない作りなので、根の長さも拡大で変わらない。押した所の判定も、描いた形を刻んで測る作りなので、根を足しても22pxの押し分けに乗る。ただし日本・台湾の辺りは**毎回「この辺りの線・国」の一覧になる**
- 国の網：網ではすでに国内の動きを矢印で描いているので、根を足すと二重になる
- 小さな地図（7日）：下の枠を置いていないので、根だけが下へ伸びる形になり、大きな地図と見え方が変わる

**他の選択肢：**

- 輪：点から外へ広がらないので、ほかの点を突き抜けない。ただしサウジの辺りは点どうしが近く、輪が重なる
- 点の横の文字（いまの「（国内N）」の横に「自分M」）：一番軽い。拡大しないと出ない（世界全体では文字を出していない）

**やった場合に失うもの（根をやめる場合）：** 「外に出す金」と「自分に沈める金」を、形の違い（横と下）で一目で見分ける、という相談書のいちばん良い所は失われる。

## 4. 積み上げの画面は要るか

**推奨：** いまは作らない。代わりに、第2段で「自分に使った金の一覧」（ドル換算の大きい順、**期間と「計画／実績」を横に出す、合計しない**）を作る。新しい画面ではなく、今のお金の一覧の絞り方として。

**理由（実測）：**

- **期間が揃っていない。** 設備投資7枚の期間は「2026年（計画）」「4〜6月」「1月1日〜6月30日」「6月30日までの1年」「会計年度の初めから6月30日まで」「会計年度の初めから7月26日まで」「期間なし」と7通り。Microsoft の1159億ドル（1年）と Alphabet の806億ドル（半年）を同じ棒で比べると、誰が一番賭けているかを**逆に読む**おそれがある
- **同じ出来事が何枚にもなっている。** トヨタの自社株買いは同じ日に5枚（実績3兆6569億円が2枚、1兆円の枠が3枚）。相手の書き方が「株主」「株式市場」などで違うため、今のまとめ方で1本にまとまるのは2枚だけ。札のまま足すと約10.3兆円、今のまとめ方の後でも約9.3兆円で、実際（実績3.66兆円＋枠1兆円）の約2倍になる
- TSMC も「年の計画600〜640億ドル」と「その中の4〜6月の実績157億ドル」が別の札で、足すと二重になる
- 主体は10ほど（TSMC・Alphabet・Microsoft・Amazon・NVIDIA・GM・トヨタ・中国・メキシコ・PIF）。棒グラフにするほどの数がまだ無い

**他の選択肢：** 期間を「年あたり」に揃え、同じ出来事を人がまとめる仕組みを先に作れば、積み上げは意味を持つ。その順番なら賛成。

**やった場合に失うもの（作らない場合）：** 「誰が一番か」を一目で見る形は、しばらく持てない。一覧を上から読むことになる。

## 5. 読む枠に1種類足すべきか

**推奨：** 足さない。枠の数字（外れ3・浅い読み5）は触らない。

**理由（実測、最新のデータ）：**

- 自分に使った金の札16枚は、**16枚とも読み済み**
- 朝の浅い読みのまま書き直し待ちなのは3枚（TSMC 年の計画、トヨタ2枚）。書き直し待ちは全体で15枚、1回5枚なので、**足さなくても3回以内に回る**
- 未読は16枚まで減っていて、前回の「未読75枚で枠が埋まる」状態ではない
- 種類を足すと、枠20枚が4つに分かれ、しかも中身はほぼ0枚の種類になる。「足りない種類の枠は他へ回す」作りなので壊れはしないが、得るものがない

**他の選択肢：** 予告の材料として重く見たいなら、種類を足すのではなく、**浅い読みの枠の中で使い道の印がある札を先に並べる**（枠の数は変わらない）。B-2（予告が外れた札）の実地確認が10/04以降なので、それを見てからでよい。

**やった場合に失うもの（足さない場合）：** 新しく入った設備投資の札が、未読の中で後回しになることはありうる（未読は新しい順なので、実際には先に来やすい）。

## 6. これからの作り方

### 6-1. いまの作りの限界はどこか

**測った値（v20.23）：** 1ファイル 24,046行・1.44MB。うち見た目の決まり 約1,370行、処理 約21,000行。処理は**全部が1つの閉じた関数の中**にあり、外から呼べる口は無い。画面の部品を1つずつ作る箇所が713、画面を描く関数が116。

**限界だと思うところ：**

- **画面ごとに部品を手で組み、丸ごと描き直している。** 画面が増えるほど手間が増える、という感覚の原因はここ。ビルドが無いことそのものではない
- **名前がぶつかっても気づけない。** 実際に一度、「今日の数字」と地図の換算で同じ名前の関数を作り、後から書いた方が黙って勝った（v20.3）。ファイルが大きくなるほど起きやすい
- **型の確かめが無い。** 札の欄を読み違えても、動かすまで分からない
- **試験のしかた：** いまは、ファイルから関数を文字として切り出して node で動かしている（今回もそうした）。動くが、壊れやすい

**限界ではないところ：** 描くこと。地図はすでに地図の部品（d3-geo）と自前の SVG で、拡大・押し分け・網まで描けている。**根も積み上げも、いまの作りで無理なく描ける**（積み上げは地図より単純）。描けない理由で作り方を変える必要はない。

### 6-2. フレームワークを入れるとしたら

どれを入れても、**データそのものは消えない。** 端末のデータは「yutatasaki.github.io」という場所ごとに保存されていて、ファイルの置き方を変えても同じ場所から配る限り残る。消える危険は**作り方ではなく、保存・合わせ・読み込み時の整え方を書き直すこと**から来る（v20.19 で見つかった「出典のメモが黙って200字で切られていた」のと同じ種類の壊れ方）。

| | ビルド無し（部品の小さな道具を assets に置いて読む。例：Preact＋htm、Lit） | ビルドあり（Vite＋React／Svelte／TypeScript など） |
|---|---|---|
| 得るもの | 画面を部品で書ける。描き直しを道具に任せられる | 部品・型・ファイル分け・試験の道具が揃う |
| 公開の手順 | **今と同じ**（押し上げたら公開） | 増える。①手元でビルドして出来上がりもリポジトリに入れる（ビルドし忘れると古いものが公開される）か、②GitHub の自動のビルドを使う（**GitHub の上での自動実行になるので、条件2に触れると考える**） |
| 同期の作り直し | 不要（今の保存と同期をそのまま呼ぶなら） | 不要（同上）。書き直すなら必要で、そこが一番危ない |
| データが消える危険 | 新しい画面が**自分用のデータの写し**を持ち、古い方に上書きして保存したときに出る | 同じ。加えて、壊れたビルドが半分動いて保存する危険 |
| 外の道具への依存 | 小さなファイル数個（今の地図の部品と同じ扱い） | npm の部品一式。更新・脆弱性の手当てが続く |
| 大きさ | **測っていません** | **測っていません** |

### 6-3. 段階的に移せるか

- **ビルド無しなら、道はある。** ただし前提が1つある：いまの処理は閉じた関数の中にあるので、新しい画面のファイルからは何も呼べない。**読むための口（札・主体・地図の振り分け・保存の入口）を1か所だけ外に出す**必要がある。地図の部品を「初めて開いたときに assets から読む」作りはすでにあるので、新しい画面も同じように読める
- **ビルドありの段階移行は、実質ない。** 2万行の閉じた関数はビルドの外に置いたままになり、新しい部品はそこから直接は読めず、結局同じ「外に出した口」を通すことになる。得るのは新しい部品の中の型と書きやすさだけで、公開の手順は全体に増える。割に合わないので「ない」と答える
- どちらの道でも、**古い画面は古い書き方のまま残る**。2万行を全部移すことは、現実的には起きない

### 6-4. 私の意見

**ビルドありへの移行には反対。ビルド無しの別ファイルは、条件付きで賛成。今回の件では、どちらもまだやらない。**

- 反対の理由：条件2（自動実行しない）を守るなら、ビルドは毎回手元で行うことになり、手順が1つ増えて、忘れたときの壊れ方が静か。得るものは、ビルド無しでもほぼ得られる
- 条件：①保存・同期・読み込み時の整え方には**一切手を入れない**。②新しい画面は**データの写しを持たず**、毎回今の口から読み、今の保存の入口から書く。③最初の1画面で、公開・オフライン・iPhone で確かめてから次へ
- 今回やらない理由：推奨案（使い道の印＋絞り＋一覧）は**新しい画面を作らない**。作り方を変える判断を、この件に乗せる必要がない。次に「まったく新しい画面」が要るときに、その画面で試すのがよい
- いまのままでも効くこと：一覧の行・絞りボタン・件数つきボタンのような、画面ごとに書き起こしている部品を**今のファイルの中で共通の道具にまとめる**。手間の原因に直接効き、失うものがほぼ無い

**やった場合に失うもの：**

- ビルド無しの別ファイルを始めた場合：書き方が2通り並ぶ状態がずっと続く。外に出した口は、うっかり書き込みにも使えてしまう。私の試験のやり方も、新しい画面はブラウザで確かめる必要が出る
- 何もしない場合：画面が増えるほど手間は増え続け、名前のぶつかりのような静かな壊れ方の危険も増える
