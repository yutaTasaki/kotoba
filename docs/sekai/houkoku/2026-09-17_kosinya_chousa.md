# 報告：ガソリン補助の額が古かった件（原因）

- 指示書：`shiji/sekai_kosinya_shiji.md`
- 調べたもの：本物のデータの写し（札・出典の一覧・取り込みの記録）、アプリのコード、出典のページ（web）

---

## 0. 先に結論

- **札の数字（36.0円）は、その週（9月10〜16日）の値としては正しい**。間違いではなく、**古くなった**
- 支給単価は**毎週水曜に公表**される。札が取り込まれたのは **9月16日（水）15:47（日本時間）**で、**同じ日に次の回（9月17〜30日・51.0円）が公表されている**
- **出典は資源エネルギー庁ではなく、民間のまとめサイト**（補助金ポータル）でした。チャット自身が `confidenceWhy` に「一次資料に当たれず、民間サイトの要約のみ」と書いています
- **この出典は「毎回必ず見るもの」に入っていません**（入っているのは7件。あとで一覧を出します）
- **「開いたか」の自己申告（`checked`）は、アプリが保存せずに捨てています**。あとから確かめられません

## 3. 聞かれた4つへの答え

### 3-1. web検索は使われたか → **使われたと考えられます。ただし確かめられません**

**測れません。** 朝の取り込みは、プロンプトをチャットに貼って返事をもらう形なので、そのときの検索の有無は私からは見られません。

**間接の手がかりは2つあります。**

1. 札の URL が `hojyokin-portal.jp` の**コラム記事**です。これはプロンプトの出典一覧にも、アプリのどこにも書かれていない URL です。**どこかで探して見つけたものです**（記憶から URL を作った可能性も残りますが、実在して中身も合っているので、開いた可能性が高い）
2. チャット自身が「**一次資料に当たれず、民間サイトの要約のみ**」と書いています。つまり**資源エネルギー庁は開けていない、と自己申告しています**

つまり「検索しなかった」のではなく、**検索はしたが一次資料まで届かず、要約サイトで止めた**、という形です。

### 3-2. 資源エネルギー庁の資料は9/16時点でまだ36.0円だったか → **いいえ。同じ9月16日に51.0円が公表されています**

- 支給単価は**毎週水曜公表**。9月16日は**水曜**
- 51.0円（9月17〜30日分）は**9月16日公表**
- 札が取り込まれたのは9月16日 15:47（日本時間）

**公表が15:47より前だったか後だったかは、私には確かめられません。** 公表時刻の記載を見つけられませんでした。

ただ、**それとは別に確かなことが1つあります。** 札が扱った 36.0円は「9月10〜16日」の分で、**取り込んだ9月16日はその最終日**でした。翌日から別の数字になることが分かっている値を、最終日に「いま広がった」という形で取り込んでいます。

なお、**資源エネルギー庁のページは私の道具からは開けませんでした**（`enecho.meti.go.jp` が 403 を返します。`category/gekihen_lp/` と `about/special/...` の両方）。要約サイトは開けました。**一次資料が開きにくく、要約サイトが開きやすい**という状況が、この事故の背景にあるかもしれません（これは推測です）。

### 3-3. 「必ず見るもの」は毎回開き直されているか → **この出典は、そもそも「必ず見るもの」に入っていません**

そして、**開き直しているかどうかは確かめられません。** アプリはチャットに「`opened`（最新の回を開いて数字まで読めたか）」を自己申告させていますが、コードにはこう書いてあります。

> `// 返ってきた checked を読む。保存しない（取り込み結果の1行に出すだけ）`

**その回の画面に1行出して、捨てています。** 9月16日の取り込みの記録にも `checked` は残っていません（記録のキーは id・date・at・batchId・same・follows だけ）。

## 4. 本当の原因（私の見立て）

**3つが重なりました。**

1. **一次資料に届かなかった**（資源エネルギー庁が開けず、要約サイトで止めた）。チャットはそれを正直に書いたが、**アプリは「要約サイトだから危ない」とは扱っていない**
2. **置き換わる数字を、置き換わる当日に取った**。週次で上書きされる値なのに、札は「広がり、3か月ぶりの高さに」と、**いま続いている状態**のように書いている
3. **アプリに「この数字はいつまでの分か」という欄が無い**。だから取り込みのときも、あとで読むときも、**古くなったことに気づけない**

## 5. `srcCadence` では判定できない（数で確かめました）

アプリはすでに `srcCadence`（出典が新しい数字を出す周期）を持っています。「出来事の日＋周期 ≦ 取り込み日 なら古い」という決まりを作れば、新しい欄なしで捕まえられるかを試しました。

| | 結果 |
|---|---|
| 周期が分かる札 | 133 |
| **「古い」に当たる札** | **69（52%）** |
| そのうち、実際に古い | ごく一部 |

`day` の札（56枚）は、9月11日の出来事を9月12日に取り込んだだけで全部引っかかります。報道は上書きされないので、これは古くありません。`day` を外しても 77枚中13枚が引っかかり、そのうち本当に置き換わる数字は3枚だけでした（準備預金・ベネズエラの週次輸出・ガソリン補助）。

**`srcCadence` は「出典がどれくらいの頻度で出すか」であって、「この数字が置き換わるか」ではありません。** だから、**新しい欄が要ります。**

---

## 6. 対策（この後、仕様書にして実装します）

1. **`validTo`（この数字はいつまでの分か）を書かせる。** 置き換わらない数字（出来事・累計・決算）は `null`
2. **札の画面に「◯月◯日までの分」と出す。** 期限が過ぎていたら「すでに次の回が出ている」と書く
3. **プロンプトの規則**：価格・補助率・為替・金利・在庫量のように**決まった周期で置き換わる数字は、その場で最新の回を開き直す。前に見た値を使い回さない**
4. **`checked` を保存する**（いまは捨てている）

**4について、先に反対を1つ書きます。** 「確認した日時を書かせれば、使い回しと区別できる」という考えには**賛成できません**。日時も `opened: true` と同じ自己申告で、**書いたことと実際に開いたことは別**です。区別はつきません。

代わりにできるのは2つです。
- **機械で確かめられるものを増やす**：`validTo`（日付なので期限切れを判定できる）、URL のドメイン（一次資料か要約サイトかを判定できる）
- **自己申告を、少なくとも捨てずに残す**：あとから「毎回 `opened: true` と言っているが、`picked` は常に0」のような癖を見返せるようにする

字数の実測は、実装の報告に載せます。
