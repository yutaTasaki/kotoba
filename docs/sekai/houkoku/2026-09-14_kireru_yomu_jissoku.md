## ⚠ 見つけたこと：予告3本が上書きされていた

**起きたこと：** 今朝 07:12（日本時間）の読む回で入った予告のうち3本が、今回（08:56）の読む回で入った新しい予告3本に**同じ番号で上書きされて**、中身が消えていた。

| 番号 | 消えた予告（07:12 に入ったもの） | 今そこにある予告（08:56 に入ったもの） |
|---|---|---|
| fc_20260914_1 | トヨタ自動車：1兆円の枠のうち3000億円以上を市場で買い付ける（期限 12/31、元 w_20260804_4） | 中国人民銀行：金準備を月50万オンス以上の刻みで積み増す（11/30） |
| fc_20260914_2 | TSMC：第3四半期に設備投資を150億ドル以上計上する（10/15、元 w_20260716_1） | 日本銀行：政策金利を1.0%から1.25%へ引き上げる（9/18） |
| fc_20260914_3 | 中国人民銀行：9月も金を15トン以上買い増す（10/7、元 w_20260907_6） | 米財務省：金への換金経路に関わる金融機関を1社以上追加指定（12/11） |

fc_20260914_4・_5（米国防総省・フーシ派）は無事。予告は全部で30本のまま（増えずに入れ替わった）。

**分かったこと（実測）：**
- 予告の番号は「fc_今日の日付_空いている一番小さい数」で、**その端末にある予告だけを見て**決めている
- 読む回の直前のデータから作り直すと、**その端末に 07:12 の予告5本が無かったとしたときだけ**、選ばれた20枚が実際と一致した。つまり、読む回を流した端末は 07:12 に入った予告5本をまだ持っていなかった
- だからその端末は _1・_2・_3 を空きと見て使い、同期で番号が同じものは新しい方が残ったので、07:12 の3本が消えた
- 札の側は無事だった（今回の20枚以外で中身が変わった札は0枚。7枚は欄の並び順が変わっただけ）。言葉も163件そろっている

**なぜ端末に予告が届いていなかったか（コードで確かめた）：**
- 予告の同期は「kotoba-data の索引にある予告の更新日時が、端末の控えより新しいか」で、取りに行くかを決めている
- ところが**索引を読み込んで整えるときに、予告の更新日時の欄を捨てていた**（概念・用語・地層・主体・聞いたこと・出典の6つは残すが、予告は並びに入っていない）。本物の索引ファイルには予告の欄がある（更新 23:56:58・30本）ので、捨てているのはアプリの側
- そのため、**どの端末も「ほかの端末が作った予告」を取りに行かない。** 取りに行くのは、自分で予告を足した（または押した）後に同期するときだけで、そのとき初めて合わさる
- 今回の流れ：07:12 に一方の端末で予告5本 → もう一方の端末は取りに行かないまま 08:56 に読む回 → 手元に無いので _1〜_3 を使う → 同期で合わさるとき同じ番号は更新日時が新しい方が残る → 07:12 の3本が消えた
- 同じ理由で、**片方の端末で予告の結果（当たり・外れ）を押しても、もう片方の端末は自分で予告を触るまでそれを見ない**はず（コードから。端末では確かめていない）

**測れないこと：** どちらの端末で流したか。

**これは今回の4段の直しで入ったものではない**（予告の同期と番号の決め方は v20.21 からこのまま）。今日初めて、同じ日に2つの端末で予告を作ったので表に出た。

**戻し方（どちらもユーザーの判断が要る）：**
- A：履歴（forecasts.json の 2026-09-13T22:12 のコミット `63c5232`）にある3本を、**新しい番号で**予告に足し戻す。作った日時・元の推定も元のまま戻せる。kotoba-data に書き込むので、許可をもらってから行う
- B：戻さない。3本の予告（トヨタ・TSMC・中国人民銀行の金）は答え合わせから外れる

**直し方の案：** 2つとも要る。今回の依頼は実測だけなので、まだ手を付けていない。
1. 索引を整えるときに予告の更新日時を残し、合わせるときも新しい方を採る（ほかの6つと同じ扱い）。これで、ほかの端末が作った予告・押した結果を同期のたびに取りに行く
2. 予告の番号に、端末ごとに違う部分（時刻と乱数など）を足して、2つの端末で同じ番号を作らないようにする（1 を直しても、同期の前に両方の端末で作れば、またぶつかるため）

**直した場合に失うもの：** 同期のたびに予告のファイル（今は約2万3千バイト）を読みに行く回数が増える。番号が長くなる（画面には出ていない）。
