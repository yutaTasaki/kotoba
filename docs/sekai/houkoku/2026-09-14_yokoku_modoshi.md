## 何をしたか

**順番：先に直して公開し、その後で戻した。** 先に戻すと、直す前の版の端末が同じ番号の予告をまた作れるため。

1. **v20.37：索引の予告の更新日時を残す**
   - 索引を読み込むとき・2つの端末の索引を合わせるときに、予告の更新日時を捨てていた。概念・用語などほかの6つと同じく残すようにした
   - 索引に予告の更新日時が無いとき（v20.36 までの端末が索引を書いた後）は、見落とさないよう、同期のたびに予告を取りに行く
2. **v20.37：予告の番号に乱数を足す**
   - 「fc_日付_空いている一番小さい数」から「fc_日付_英数字8文字の乱数」にした（例 fc_20260914_lzvu5gsq）。端末にある番号とぶつかったら作り直す
3. **予告3本を戻した**（kotoba-data に書き込み）
   - 07:12 の版（履歴 63c5232）にあった3本を、**新しい形の番号で**予告に足した。中身・作った日時・元の推定は元のまま。変えたのは番号と更新日時だけ
   - 索引の予告の欄を「33本・今の日時」にした

## 意味

- 両方の端末が v20.37 になれば、ほかの端末が作った予告・押した結果を、同期のたびに取りに行く
- 同期の前に両方の端末で予告を作っても、番号がぶつからないので消えない

## やった場合に失うもの

- 同期のたびに予告のファイル（今は約2万4千バイト）を読みに行く回数が増える。索引の予告の欄が空の間は毎回読む
- 番号が長くなった（fc_20260914_lzvu5gsq）。画面には出ていない。答え合わせの JSON では生成がこの番号を写す
- 戻した3本の更新日時は今日の書き込みの時刻になった（作った日時は元のまま）
- 同じ中国人民銀行の金の予告が2本並ぶ（「9月も15トン以上」と「月50万オンス以上の刻み」）

## お願い

1. **iPhone と PC の両方を v20.37 にしてください**（設定 → 世界の一番下）。v20.36 のままの端末は、ほかの端末の予告を取りに行かず、索引の予告の欄をまた空にします
2. 両方そろったら、どちらの端末でも世界 → 予告に **33本**（トヨタ・TSMC・中国人民銀行の金の3本を含む）が出るか見てください
3. そろうまでは、予告を作る読む回は片方の端末だけで流すのが安全です

## 測れていないこと

- 実際の端末どうしの同期で、v20.37 の端末が予告を取りに行くこと（本物の GitHub での2台の同期は試していない。コードを取り出した試しと、試しのページだけ）

## 残り（今回は触っていない）

- **札・概念・聞いたことの番号も、同じ「空いている一番小さい数」の作り**（札は w_出来事の日付_数、概念などは作った日付_数）。札の月ファイルと概念は、索引の更新日時が残っているので同期のたびに取りに行く。ただ、同期の前に両方の端末で同じ日付の札を入れると、同じ番号になる余地はある（今日のようなことが起きたかは数えていない）
