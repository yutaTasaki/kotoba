# データの置き場所を変えるか

日付：2026-09-14　元の指示書：`shiji/shiji_database_2026-09-14.md`（調べるだけ）　元の報告：[データ量は1万日もつか](2026-09-14_datalyou.md)
**直していない。** 今のコード（v20.40）と kotoba-data（読むだけ）、候補のサービスの公式の資料（2026-09-14 に読んだ）で調べた。

---

## 結果（先に）

1. **勧める案：データベースは使わず、GitHub のまま「読み方と分け方」を直す（案B）。** 5つの限界のうち、1・2・4 はほぼ消え、3 は約5分の1に、5 は伸びを遅くできる。**GitHub の履歴（全部の版が残る）・無料・自分のサーバー無し・アカウントを増やさない**を全部守れる
2. **データベースにしても、5つの限界のうち確実に消えるのは 1・2・4 だけ。** 3（全部の言葉をメモリに置く）は、網・相談・関連づけが全部の言葉を使う作りを変えない限り残る。これは置き場所ではなく作りの問題で、GitHub のままでも同じ直しで解ける
3. **データベースにすると失うもの：**
   - **GitHub の履歴のように、全部の版は残らない**（データベースは上書き。Supabase の無料の枠は自動のバックアップも無い）
   - 通信が切れたとき、まだ取っていないデータが見られない（今は全部端末にあるので、開いた後に切れても使える）
   - アカウント・鍵・利用規約が1つ増える。Supabase の無料の枠は「1週間使わないと止まる」
   - 1万日後は無料の枠を超える見込み（Supabase 無料 500MB に対し、1万日で数百MB〜1GB 超）
4. **Cloudflare D1 は反対。** 画面から直接は使えず、間に自分の小さなサーバー（Worker）を作って置く必要があり、「自分のサーバーが無い」「ビルド無し」を崩す
5. **オフライン：今もホーム画面から開けない**（Service Worker が無い。コードで確かめた）。開いた後に通信が切れても、今は端末に全部あるので使える。**データベースで「必要な分だけ取る」にすると、切れた後に取っていない分が見られなくなり、今より下がる**

## 1. 5つの限界は、何が消えて何が残るか

| # | 限界 | データベースにすると | GitHub のまま直すと（案B） |
|---|---|---|---|
| 1 | 読む欄を開くたびに全部の月を取りに行く（約200日後） | **消える**（読む枠の候補だけ取る問い合わせにできる） | **消える**。端末にある月は、索引の日時が変わっていなければ取りに行かない（ふだんの同期と同じ決まり）。さらに候補のある月だけ読む（索引に月ごとの数を持つ） |
| 2 | 本を数千枚入れると、1件保存ごとに月のファイル丸ごとを送る | **消える**（1件ずつ書く） | **ほぼ消える**。言葉のファイルを「月」ではなく「200件ごと」などに分ければ、1回に送るのは1ファイル約0.8MB まで |
| 3 | 起動のたびに全部の言葉をメモリに置く（1万日×5件/日で約190MB） | **残る**。網・相談・関連づけが全部の言葉を使う作りのままなら、全部を取ってきてメモリに置くことになる（通信の分、今より遅い） | **約5分の1に減る**。言葉の中身の81%はつながり（本物の173件で実測：1件1,956字のうち、つながりを除くと361字）。つながりは開いたときに読むようにすれば、1万日×5件/日で JSON 約17MB（今の形は約93MB）、17件/日で約59MB（約317MB） |
| 4 | ファイル丸ごとを書き直す所（予告・概念・数字） | **消える**（1件ずつ書く） | **消える**。予告は年ごと、端末の数字は月ごと、概念の「この札に出てきた」は札の月ファイルから数え直す |
| 5 | リポジトリが1GB を超える（約2,000日後） | **消える**（GitHub を使わなければ）。代わりにデータベースの大きさが増える（1万日で数百MB〜1GB 超） | **遅くなるが残る**。書き直すファイルが小さくなり、変わらない data.json・training.json を書かなくすれば伸びは減る。どれだけ減るかは**測れません**。超えそうになったら、年ごとに新しいリポジトリへ移し、古いものは読むだけで残す案がある |

**3 について大事なこと：** 全部を毎回読む必要があるのは、網（全部の言葉のつながり）・相談（全部の言葉から選ぶ）・関連づけ（全部の言葉と比べる）が全部を使うから。データベースに移しても、この3つを「必要な分だけ使う」作りに変えない限り、全部を取ってくる。**この作り直しは、置き場所を変えなくてもできる。**

## 3. 費用と、止まったときのこと

### 無料の枠（公式の資料）

| サービス | 無料の枠 | 超えたら |
|---|---|---|
| **GitHub（今）** | 非公開のリポジトリは無料。1ファイル100MiB まで。リポジトリは1GB 未満が理想・5GB 未満を強く推奨。呼び出しは1時間5,000回・同時100まで | 目安を超えると GitHub から連絡が来ることがある |
| **Supabase** | データベース 500MB・ファイル 1GB・通信 5GB/月。**1週間使わないと止まる**。自動バックアップ無し | Pro 月25ドルから（データベース 8GB 込み、超えた分 1GB 0.125ドル） |
| **Firestore** | 保存 1GiB・読み 5万回/日・書き 2万回/日・通信 10GiB/月。1件（文書）は 1MiB まで | 従量課金（料金は地域で変わる。**今回は確かめていない**） |
| **Cloudflare D1** | 保存 5GB・読み 500万行/日・書き 10万行/日（**使うには Worker が要る**） | 有料プラン（読み・書き・保存の従量） |

### 1万日後の見込み

データ量の報告の見込み（字下げつき JSON）：言葉 200〜675MB、札 360〜730MB、ほか数十MB。データベースに入れると、字下げは無くなるが、検索のための索引の分が増える（どちらが大きいかは**測れません**）。

| | 1,000日 | 3,000日 | 1万日 |
|---|---|---|---|
| 言葉5件＋札10枚/日 の JSON（字下げなし・つながり込み） | 約28MB | 約85MB | 約280MB |
| 言葉17件＋札20枚/日 | 約70MB | 約210MB | 約700MB |
| Supabase 無料（500MB） | 収まる | 収まる | **多い場合は超える**（超えた後は Pro で月25ドル＝1年300ドル） |
| Firestore 無料（1GiB） | 収まる | 収まる | 収まる見込み。ただし読みが1日5万回に当たらないように作る必要がある（網を開くたびに全部の言葉を読むと、5万件で1回に5万回） |

### 止まったとき・無くなったとき

- **データベース：** 止まっている間は、端末に控えていない分は見られない。無くなったら、自分で書き出した控えが無ければ**データを失う**。Supabase の無料の枠は、1週間使わないだけで止まる（戻せる期間などは**今回確かめていない**）
- **GitHub（今）：** 止まっている間も、端末に全部あるので見られる（同期だけ止まる）。無くなっても、端末と、複製（`git clone`）に全部の履歴が残る

### GitHub は残すのか

- データベースに移すなら、**消えないために GitHub を控えとして残す**のが前提になる。すると置き場所が2つになり、2つを合わせる仕組み（どちらが正しいか、片方だけ書けたとき）を作る必要がある。今日まで同期で何度も起きた「片方だけ」の事故の場所が増える
- GitHub を置き換える（捨てる）なら、「全部の版が残る」を失う

### 勧める：案B

- **5つのうち困る順の 1（約200日後）を、B1 だけで今すぐ消せる。** 小さい直しで、失うものは「古い月の反映が次の同期まで遅れる」だけ
- データベースにしても 3 は残る。3 を解くのは「全部を使う作りを変える」ことで、それは GitHub のままでもできる（B3）
- **「データが消えない」を一番守れるのが GitHub の履歴。** データベースに移すと、これを自分で作り直すか、GitHub と2つの置き場所を持つことになる
- 費用・アカウント・止まる心配が増えない
- 1つずつ出して、1つずつ戻せる

**反対：** 案E（自分のサーバーが要る）。案C・D は反対ではないが、今は勧めない（上の理由）。案B で 3 と 5 が本当に解けないと分かったら、そのとき考え直す

## 6. どう移すか

### 案B（GitHub のまま）

| 直し | 移し方 | 途中で失敗したら | 戻せるか |
|---|---|---|---|
| B1・B2・B6 | データの形は変えない（読み方だけ） | 何も失わない | 前の版に戻すだけ |
| B3 | データの形は変えない（つながりを読む時期だけ変える） | 何も失わない | 戻せる |
| B4・B5 | 新しい形のファイルを**別の場所に書き**、両方の端末が新しい版になってから読み先を切り替える。古いファイルは消さずに残す（v7.4 の言葉の月ファイルへの移し替えと同じ手順） | 古いファイルが残っているので、読み先を戻すだけ | 戻せる（古いファイルが残っている間） |

### 案C・D（データベース）を選ぶ場合

- 移し方：GitHub のファイルを読んでデータベースに入れる。**しばらくは両方に書き**、読み先だけを切り替える
- 途中で失敗したら：GitHub が正のままなので失わない。データベースの側を消して、やり直す
- 少しずつ移せるか：できる（例：札だけ先に）。ただし種類ごとに置き場所が違う期間は、合わせる仕組みが2通りになる
- 戻せるか：GitHub に書き続けている間は戻せる。**GitHub に書くのをやめた後は、データベースから書き出して GitHub の形に戻す仕組みを作らないと戻せない**
